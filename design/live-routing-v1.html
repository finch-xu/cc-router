为什么是三段而不是 hub

  • 旧图中间的 hub 只是装饰；真正决定路线的是虚拟模型。把它画成一列，「哪个客户端用哪个槽位、槽位落到哪家」一眼可读。
  • 中间列放进凹陷的「cc-router」机箱，表达虚拟模型属于本机。
  • 客户端节点副标题显示会话数与正在跑的子 Agent 数（来自 Agent 监控）；后台任务的粒子小一号、灰色。
  • 左列只列活跃客户端：当前时间窗内发过请求或正有请求在途。没用过的（如 OpenCode）不占位；第一次发请求时节点淡入、连线重排，窗口内没动静了再淡出。

动效纪律

  • 粒子只在真实请求在途时出现；页面空闲即完全静止（无循环装饰动画）。
  • 粒子 0.35s + 0.45s 走完两段；完成时节点短闪 + +18.2k 浮字，失败闪红。
  • 「暂停」冻结画面但继续计数，恢复时一次补齐；prefers-reduced-motion 下不画粒子，只更新数字和线宽。

落地需要的数据

  • 请求用途后端判定后随事件下发：hooks 时间线（UserPromptSubmit / PostToolUse / SubagentStart / PreCompact）定会话与轮次；子 Agent 与小模型后台任务再看请求体特征（tools 数、max_tokens、system 指纹），标「推断」。只存工具名，不存命令或文件内容。
  • route_attempt_started/finished 补 request_id（配对不再靠猜）、client_tool；finished 补 token 四项、首字 / 总耗时、HTTP 状态。
  • 首屏用 list_requests 最近 N 分钟回填图表与活跃客户端列表，之后纯靠事件增量。
  • 订阅状态、冷却剩余、限额进度已有（subscription_state_changed + SubscriptionDto）。
